Baseline: feat/mobile-customer-parity at 61a62c5. Reference: read-only feasta-web-reference at 0c3f6f5.

## Inspection and intended changes

Inspected the approved booking selection serializer, preparation summary/customization, FEASTA card/button components, web customer-booking-agreement parser and booking-payment-agreement-review component, event-customization-experience invalidation, and backend submit-booking-request / booking-payment-agreement.

Backend constraints: getBookingPaymentAgreementDisclosures accepts the same allowlisted selection as submission, including clientRequestId. It authenticates and validates account, providers, packages, policy and selection. The disclosure-only branch precedes agreement acknowledgement validation and booking writes. Existing request IDs can return a replay envelope without agreements: reconciliation is required. Disclosure schemaVersion=1 / timingSchemaVersion=3; keys are SHA256 hex; one agreement per provider (1-21); serviceNames 1-32, each at most 200 characters. Timing is event minus 72/48/24/24 hours. Amounts are safe integer centavos, upfront plus remaining equals gross. Deposit-default allocation is server-generated 70/20/remainder percent of upfront; full-payment agreements have zero remaining and null allocation. Acknowledgements contain only providerId and agreementKey.

Planned source changes: new shared/models/booking_agreement.dart, features/customer/booking_agreement_controller.dart, features/customer/booking_agreement_review_screen.dart; add disclosure-only method in feasta_repository.dart and safe review link in booking_summary_screen.dart. Add focused model/controller/widget/integration tests. Preserve the M4.1 serializer and preparationOnly=true normal route. Reuse existing FEASTA cards, buttons and emerald theme. No submission, new payment, refund-policy review or durable submission-attempt persistence.


## Implemented behavior

The preparation-only summary now offers Review Booking & Payment Agreements, opening a separate review page with existing FEASTA cards/buttons and emerald styling. No active Submit Booking control is introduced. The page shows each server provider's name, services, tier, service total, required upfront payment, remaining balance, event start, deposit cutoff (when applicable), balance due, hard payment deadline, preparation start and payment-default terms. Amounts are formatted directly from integer centavos; no local authoritative amounts or aggregate event total are invented. All deadlines display in Asia/Manila independent of device timezone.

FeastaRepository.getBookingPaymentAgreementDisclosures uses the existing asia-southeast1 Functions instance and bootstrap App Check activation with a 30-second callable timeout. Only getBookingPaymentAgreementDisclosures is invoked by this review. BookingAgreementRequest snapshots the approved M4.1 allowlisted payload including clientRequestId, date, times, selections, tier, theme and addonIds. No price, coordinates, quantity metadata, agreement policy snapshot or financial authority is added to the request. Account authorization/verification is enforced by the server; unauthenticated review is rejected locally as well.

The parser validates the disclosure envelope, nonempty agreements array, unique providers, exact disclosure field allowlist, schemas, SHA256 keys, services, safe integer centavos, totals and ISO UTC timing relationships. It validates the actual eight-field server paymentDefaultAllocation (schema, deposit basis, three basis-point rates and three allocated amounts), not just the reduced web TypeScript annotation. It validates server amounts rather than calculating amounts for display. Full-payment disclosures require null allocation and zero balance. Missing agreements is an explicit reconciliation state, including existing-booking replay envelopes. Empty/malformed disclosures fail closed.

Each checkbox starts unchecked and maps only its server providerId to its server agreementKey. The controller exposes acknowledgement maps with exactly these two keys only when every current agreement is acknowledged. No consent is read from drafts or persisted. There is no submission integration in this phase.

The transient selection signature includes owner, all serialized selection fields and local add-on context (including provider/quantity changes). One random clientRequestId is retained for repeated loads of the same screen's selection context. Edits/account changes rotate that context, invalidate consent and cancel the relevance of previous responses. Identical selection updates preserve current state; refresh clears consent pending new validated disclosures. Leaving the review discards consent. This is deliberately not M4.4 durable submission-attempt handling.

Generation guards prevent old successes/errors from overwriting newer state. Concurrent repeated loads share one pending future; disposed or superseded queued loads are skipped. Disposal cancels expiry timers and suppresses late notifications. Deposit cutoff or hard deadline expiry revokes consent and requires reloading; current-time checks also prevent exporting expired acknowledgements before a timer executes. A failed refresh cannot retain accepted agreements.

Loading, retry and reconciliation states use actionable messages. Callable errors cover unauthenticated, verification/account eligibility, unavailable provider/package, invalid selection, network, rate limits and timeout. BOOKING_PAYMENT_AGREEMENT_REQUIRED and BOOKING_PAYMENT_AGREEMENT_CHANGED require current review; raw backend exceptions are not shown.

## Provider-completeness correction (2026-10-19)

The independent review found that uniqueness alone did not establish complete provider coverage. The agreement controller now requires an exact expected/returned provider-ID set match before exposing agreements. Missing, unexpected, duplicate, or unreconciled providers fail closed, clear consent, and require refreshing agreements or returning to selections. Preparation data is preserved.

The expected set starts with the selected catering provider. BookingAgreementRequest captures an immutable local add-on ownership comparison snapshot separately from its unchanged M4.1 transport JSON. On every load, the screen uses FeastaRepository.resolveBookingAgreementProviders, which refreshes each distinct selected add-on through the existing getEligiblePreparationAddon server-only reads. Current ownership must match the captured providerId and source; local metadata alone never establishes ownership. Multiple add-ons from one provider require one agreement, and catering-owned add-ons do not add another provider. Missing metadata, changed ownership, unavailable records, and lookup failures block review. Server-side booking selection and payment agreement validation remain authoritative; no backend contract extension is needed.

Generation/disposal guards cover both ownership resolution and disclosure loading. The exact immutable request supplies the add-on IDs for ownership refresh and the callable payload. An ownership change requires selection reconciliation rather than silently accepting another provider. Fresh loads repeat ownership validation and start without consent.

Added booking_agreement_completeness_test.dart (17 tests), plus repository ownership and partial-response/retry widget regressions (2 tests). Coverage includes A/B complete, only A, only B, unrelated C, equal-count substitution, unexpected extras, duplicates, shared marketplace ownership, catering-owned add-ons, unresolved/changed ownership, successful retry without restored consent, immutable snapshots, stale ownership resolution, account switching during a pending disclosure, and a late response after expiry.
