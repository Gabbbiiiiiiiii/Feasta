## Historical eligibility

`provider-payment-service.ts` reads canonical `payments` with the trusted approved provider's `providerId`, optional exact payment `status`, descending `createdAt` and document ID. It does not filter on event date or booking status. `provider-payment-normalization.ts` accepts past events and all recognized provider-request/main-event statuses, including completed and cancelled. It requires a parseable event date and recognized statuses; missing or obsolete status values still fail validation. Booking completion or a booking's paid flag does not create a payment transaction.

The page initially loads payments and finance concurrently. Filter server actions call only `getProviderPaymentRows`; they do not refresh finance or summary aggregates. The client preserves the summary and rejects stale responses using request IDs.

## Confirmed exclusion mechanisms, not confirmed production diagnoses

- Ownership: only exact canonical `payment.providerId` matches are queried. Legacy `recipientProviderId` alone is insufficient. Related provider requests must belong to the same trusted provider.
- Linkage: `providerRequestId` must be valid and resolve. `mainEventId`, or `bookingId` only when the former is null/absent, must resolve. The request's event and customer must match the payment; the main event must have the same customer. An invalid non-null `mainEventId` does not fall back to `bookingId`. If both event fields are populated, the normalizer uses `mainEventId`; it does not separately check the unused alias.
- Canonical fields: stored `paymentId` must match the document ID. Positive safe integer `amountInCentavos`, PHP currency, canonical payment type/status, supported refund status, parseable `createdAt`, event date, and booking statuses are required. Legacy peso-only `amount`, missing stored payment ID, or missing canonical linkage is insufficient. Display names and service names have safe fallbacks and do not cause exclusion.
- Ordering: Firestore `orderBy(createdAt)` excludes documents without that field before normalization. Normalization accepts date strings, but cursor encoding accepts only Date/Timestamp-like values; legacy string timestamps can therefore normalize yet produce a null cursor at a page boundary. Mixed timestamp types also do not form a reliable chronological history.
- Duplicates: all normalized rows sharing a provider request within the current raw page are removed. Malformed duplicate rows do not participate. Duplicates across pages/status filters can escape list detection; detail lookup rejects any provider request with more than one canonical payment document, even across providers/statuses. This existing discrepancy was preserved.
- Pagination: each page consumes at most `pageSize` raw documents after fetching one lookahead. It does not refill rejected rows. `skippedMalformedCount = raw page length - displayed length`, including duplicate exclusions. The cursor advances from the last consumed raw document, not the last displayed payment. Thus a page can be sparse or empty and still have Next. Skipped counts exclude missing-order-field records and documents outside the provider/status query. Summary counts aggregate raw documents, not validated displayed rows.

Six raw/summary records versus four displayed rows could reflect status selection, normalization, duplicates, or a different snapshot. Source confirms these mechanisms but does not establish which occurred in the screenshot. No records were invented and validation was not relaxed.

The business contract (`docs/domain/payment-business-contract.md`) permits deposit and remaining-balance transactions for one booking. Duplicate-provider-request rejection may therefore hide legitimate split payments. Do not deduplicate, merge, or delete those documents automatically. Reconcile canonical transaction identities and payment types against trusted evidence in a separate reviewed change, including consistent list/detail rules and pagination tests.

## Latency and validation limits

Filtered reads necessarily await provider authorization, one bounded payment query, then relationship fetches. Request and event IDs are deduplicated; both relationship groups are fetched concurrently through batched `getAll`. Initial summary metrics and rows also run concurrently. No proven redundant wait was found in the filtered path, so no speculative caching or financial service changes were introduced. Live authentication, Firestore indexes/network latency, and server-action scheduling require production timing evidence; skeletons do not shorten those requests.

Component tests cover all seven filters, stale responses, URL popstate restoration, cursor history, pending skeletons, responsive layout classes, reduced-motion classes, focus retention, count announcements, errors/retry and empty states. Historical normalization tests cover paid/refunded records with past events and completed/cancelled bookings. Browser viewport rendering, real screen-reader speech, and live network timings remain manual checks; JSDOM does not render responsive CSS or emulate browser history traversal timing.
