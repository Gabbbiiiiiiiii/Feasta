## Totals finding and handoff

The dormant `_createBookingRequestLegacy` writer and the authoritative backend write `totalAmount` as catering subtotal, with separate `cateringSubtotal` and `estimatedEventTotal` fields. `BookingModel.fromDoc` currently reads only `totalAmount`; booking detail views and payment projections consume it as a booking total. A marketplace add-on event can therefore be represented with catering-only money where a whole-event amount might be expected. The dormant summary's legacy estimate also uses `package.price` rather than the selected tier.

M4.1 does not migrate historical booking reads, recovery, cancellation or payment workflows. The active preparation estimate uses the selected tier and priced selected add-ons, excludes unknown/customer-arranged costs, and now explicitly says it is not a confirmed whole-event total. Future display/payment work must distinguish provider-request charges from aggregate event amounts using trusted server projections.
